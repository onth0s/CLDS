Good — and it's worth pausing on _why_ it's the correct next step rather than just a nice-to-have, because the reasoning maps almost exactly onto the structural-enforcement argument you've been building in CLDS.



### Why this is the load-bearing move, not a polish pass

The provenance report you're looking at — platform, Python version, Lean build time, test counts — is _evidence of execution_, but it is evidence of the wrong thing. It tells you a script ran and things happened. It does not tell you which claimed capability each of those things corresponds to. "124 tests: 23.90s" is a compliance signal in exactly the sense your Anti-Pattern 14 (Assertion-Gated Success) describes: a terminal success marker whose apparent coverage exceeds its actual verification coverage. You don't know from that line whether those 124 tests exercise Front 08, or whether Front 08 has zero coverage and the 124 tests are all hammering Front 02 six different ways. The number is real, but its evidentiary weight relative to the claim "I implemented 101 papers" is undetermined without a mapping layer.

This is the same gap REP Step 6.5 exists to close at the plan-implementation level, except here the object being audited isn't "does the code match the ratified plan" — it's "does the log match the claim," which is one level more basic and, honestly, more dangerous to leave unaudited, because logs _look_ like proof in a way that plain assertions don't. A CA saying "I implemented it" is legible as a claim requiring scrutiny. A CA saying "here's a build log with 124 passing tests" _reads_ as evidence and short-circuits scrutiny — that's precisely the "accidentally hilarious" tribunal-exhibit quality you flagged. The humor is doing real diagnostic work: it's funny because the report is over-performing its epistemic authority relative to what it actually demonstrates.



### What the manifest actually needs to be

Not a log. A **claim graph** with mandatory edges, where the edges are the thing under audit, not the nodes. Concretely, each row needs:

FieldFunction**Capability claim ID**e.g. `Front-08` — the atomic unit of "I implemented X"**Specification anchor**pointer to the exact section/paper/requirement this claim discharges**Implementation anchor**file + symbol/function, not just "this repo"**Test anchor**which specific test IDs exercise _this_ claim — not "the suite passed," but the named subset**Formal status** (where applicable)theorem name + Lean/Coq build target, `sorry`-free or not**Commit hash**pins the claim to an immutable artifact, not a moving branch**Executable evidence**the actual command that reproduces the result, runnable independently of the CA's narration The critical design constraint, and this is where it converges hard with your Ratification Vault philosophy, is that **the manifest must be falsifiable by someone who isn't the agent that built it.** If the manifest is generated by the same CA that wrote the implementation, self-reporting its own coverage, you've just relocated Anti-Pattern 14 one layer up — now the _manifest itself_ is an assertion-gated success artifact, claiming "I've mapped everything" without independent verification that the mapping is complete or honest. This is structurally identical to the concern you flagged for the autonomous self-refinement pipeline: correlated agents don't constitute independent audit. A manifest-builder script and a claim-verifier need to be different processes with different failure modes, or ideally the verifier needs to be something that _runs_ the executable evidence field and checks the output against an expected shape, rather than trusting a CA's assertion that it checked.



### The query surface is the actual test of the design

"Show me the evidence chain for Front 08, from specification to executable behavior" is the right acceptance criterion because it's a **negative-existence-provable** query — if Front 08 has no test anchor, that's immediately visible as an empty cell, not a buried gap in a 101-item wall of green checkmarks. This is the same principle as your dead-end detection finding in diegetics (D-INGEST-06): a system that can print "Dead-end detected" while structurally incapable of detecting dead-ends under any input is dangerous _because_ the success signal is decoupled from the actual verification event. A Verification Manifest with a hole in row 08 is honest in a way "124 tests passed" is not, because the hole is queryable rather than laundered into an aggregate.



### Practical build note, in Moon-version terms

Full auto-generation of this manifest across 101 papers / 14 fronts is Alpha Centauri. The Moon version is probably:



1. A fixed schema (the table above, or close to it) as a flat file — YAML or a simple SQLite table, given your existing comfort with SQLite from sempath — not a generated document, at least initially, since generation reintroduces the self-reporting problem before you've even validated the schema is right.
2. Manual population for a handful of fronts first — enough to find out whether the schema's columns are actually the right decomposition, before spending the effort to automate extraction.
3. Only after the schema has survived contact with a few real fronts: a script that _checks_ manifest completeness (all claim IDs have all fields populated, all commit hashes resolve, all test anchors correspond to test IDs that actually exist in the suite) — this checker is cheap, mechanical, and closer to apodictic than anything that tries to _generate_ the mapping from CA self-report.
The generation-vs-checking split matters a lot here: checking "does this manifest row have a real commit hash and a real test ID" is a structural, verifiable-by-construction operation. Generating "here is the correct mapping from Front 08 to its tests" is exactly the kind of claim that needs to come from ratified human judgment or from a genuinely independent process, not from the same CA narrating its own coverage.
